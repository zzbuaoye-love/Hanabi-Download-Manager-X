# 下载内核

HDMX 使用双内核架构。`KernelManager` 是统一路由器，UI、浏览器扩展 API 和系统服务都通过它下发命令。

## 内核清单

| 内核 | 全名 | 版本 | 通道 | 内核 ID | 实现 |
| --- | --- | --- | --- | --- | --- |
| NSFX | Next Speed Force X | 3.0.0 | Release | `nsfx_v1` | Dart 引擎，`dart:io` / `rhttp` 双适配 |
| NeoNSF | Neo Next Speed Force | 1.0.0 | Beta | `neo_nsf` | 常驻 `.NET 8 NativeAOT` 侧车 `HanabiNeoNSF.exe` |

- **NSFX** 是默认内核，始终启动，并持有唯一的浏览器扩展 HTTP 监听器，作为长期稳定兜底。
- **NeoNSF** 是并行开发的新内核，数据面直接在原生侧写文件，不经过 Dart。

## 选择模式

设置页的「下载内核」区块和托盘菜单都可以切换，共三种模式：

| 模式 | 值 | 行为 |
| --- | --- | --- |
| NSFX | `nsfx_v1` | 全部新任务交给 NSFX |
| NeoNSF | `neo_nsf` | 全部新任务交给 NeoNSF，不会静默换核 |
| Auto | `auto` | 双内核自动路由，仅在 NeoNSF 接收任务前可回退 NSFX |

> [!IMPORTANT]
> 切换内核只影响新任务。任务创建后由不可变 `kernelId` 绑定原内核，不做运行中迁移，也不允许两个内核同时写同一个目标文件。
> 原生侧确认接收任务后，任何模式都不再自动换核。

暂停、续传、取消、重命名和移动都按任务 `kernelId` 回到原内核；任务列表、进度事件、完成事件和统计在路由层聚合。

## NeoNSF 技术选择

NeoNSF 使用常驻 .NET NativeAOT 侧车，而不是在 Dart 中继续堆叠 isolate：

| 项目 | 说明 |
| --- | --- |
| 网络栈 | `HttpClient` / `SocketsHttpHandler`，提供连接池、TLS、HTTP/1.1・2・3、系统代理与显式代理 |
| 文件写入 | 原生异步 `FileStream` / `RandomAccess.WriteAsync`，Range 字节直接写入 `.neonsf.partial` |
| 控制面 | JSONL stdin/stdout，Dart 只传控制命令并消费增量事件 |
| 发布形态 | NativeAOT 单文件 `HanabiNeoNSF.exe`，用户无需安装 .NET 运行时 |

### 执行策略

所有任务走同一条起手：一次 `GET Range: bytes=0-`。这一个请求同时回答长度、Range
能力、验证器和重定向后的最终 URL，而它的响应体**就是下载本身**——没有任何一次往返
被浪费在预探测上。

| 探测响应 | 行为 |
| --- | --- |
| `206` 且长度 ≥ 8 MiB | 分块并发；探测响应直接充当 lane 0 的第一个分块 |
| `206` 且长度 < 8 MiB | 单连接流式写完，不再发第二个请求 |
| `200` | 服务器不认 Range，直接把这条响应流完 |
| `416` | 退回无 Range 的普通 GET（同时覆盖零字节资源） |

已有断点续传状态时，探测改用 `Range: bytes=0-0`，只为校验验证器，代价可忽略。

> [!NOTE]
> 早期版本用 HEAD 做预探测。HEAD 在拿到任何字节前先付一次完整往返，且被大量 CDN
> 与对象存储拒绝或直接黑洞——被黑洞时要耗尽整个读超时才会降级，一个 200 KiB 的
> 文件可能卡满 30 秒。这正是小文件劣势的直接来源。

### 分块与车道

不再预切分段。**初始只有一个覆盖全文件的分块，靠按需分裂扩展**：

| 项目 | 行为 |
| --- | --- |
| 初始规划 | 单块 `[0, 总长-1]`，由探测响应直接开始流式写入 |
| 扩展方式 | 新车道上线时切走在途最大分块的尾巴（两半都需 ≥ 1 MiB） |
| 请求总数 | **等于实际启用的车道数**，这是理论下限 |
| 连接隔离 | 每条车道独占一个 `SocketsHttpHandler` |
| 车道上限 | `maxConnections`，硬上限 16 |

预切是纯成本：每一条分块边界都是某条车道连接上的一次额外顺序请求。实测在高延迟
链路上，预切 16 块让 72 MiB 传输**慢于**单条不分段的流。分裂式扩展只产生「每条真正
上线的车道一次额外请求」，并且切点用的是实时进度，而不是任何字节流动前的猜测。

车道独占连接池是关键。.NET 的连接池以 handler 为单位，共用 handler 时 HTTP/2 会把
全部 Range 复用到同一条 TCP 上——同一个拥塞窗口、同一条队头阻塞链路、服务端的
单连接限速一视同仁，并发分段的收益归零。`EnableMultipleHttp2Connections` 只在触及
流上限（通常 100）时才开新连接，8 或 16 路永远碰不到。

### 自适应车道调速器

**并发数不是配置值，是测量结果。** 传输从 1 条车道起步，只在增加车道被证明有收益时
才升档：

| 阶段 | 行为 |
| --- | --- |
| 热身 | 前 1.5 s 不做任何判断，让首条连接走完 TCP 慢启动 |
| 升档 | 每 1.2 s 采样一次；吞吐较上一档提升 ≥ 15% 才再加一条车道 |
| 收敛 | 提升不足 15% 时退回一档并停止，本次传输不再调整 |

> [!IMPORTANT]
> 固定并发数在两个方向上都是错的，这是实测结论而非推断。同一条链路上：单连接跑不满
> 时 4 路比 1 路快 **2.5 倍**；而链路已被单连接跑满时，8 路反而慢到 **7 倍**，且出现
> 3.5 s → 18.9 s 的灾难性离群。代理/单出口网络（国内常见）几乎总是后者。
>
> 调速器让两种情况都收敛到接近最优：在已跑满的链路上它停在 1–2 路，性能与单连接持平；
> 在单连接吃不满的链路上它爬到能吃满为止。

`headers` 事件的 `connectionCount` 是当前值、`maxConnectionCount` 是上限；
`progress` 事件持续汇报实时车道数，UI 显示的线程数据据此更新。

### 磁盘写入

- 分块目标文件创建后立刻 `FSCTL_SET_SPARSE`，再 `SetLength`。
  NTFS 的 `SetLength` 只移动 EOF，不推进 ValidDataLength；随后向高偏移写入时内核必须
  **同步零填充**中间空洞。并发分段里偏移最高的那条车道会触发接近全文件长度的零写。
  实测 1 GiB 预分配后写文件末尾：稠密 **398 ms**，稀疏 **1 ms**，且该停顿随文件大小线性增长。
- 每条车道用 `ArrayPool` 的 512 KiB 缓冲攒满再落盘，而不是每 64 KiB 一次异步写。
- 计数只在写入完成后推进，缓冲中未落盘的字节永远不计入检查点。

### 持久化

NeoNSF 使用独立目录 `~/.hdmx/kernel/neo_nsf/`，与 NSFX 数据互不干扰：

- `.neonsf.partial`：稀疏预分配的分块写入目标
- `.neonsf.state`：检查点 v2，记录分块列表、ETag、Last-Modified、总长度与最终 URL

检查点由独立的 1 秒定时器落盘，不在读循环里 await；进度事件同理走独立的 250 ms
定时器，热路径上没有任何锁。

重启时活动任务恢复为暂停状态，不会被 NSFX 误读。

### 稳定性规则

- partial 文件关闭后才原子替换最终文件；`expectedSha256` 存在时先校验再替换。
- **分段级重试**：单条车道失败只重试它自己那一块，并回收该车道的连接以换一个边缘节点；
  致命错误（Range 能力丢失、验证器变化）才通过链接取消令牌中止全部车道。
- 并行恢复必须通过 ETag 或 Last-Modified 验证；验证器变化时清空重建。
- 连接中断、读取超时、HTTP 408 / 429 / 5xx 可以退避重试。
- 慢车道熔断：某车道速度低于「任务均速 ÷ 车道数 ÷ 8」且持续 20 秒时断开重连，
  仅在 ≥ 2 条车道活跃时生效，单连接任务永不触发。
- 重定向只在探测阶段解析一次，后续分块统一使用最终 URL，避免 8 路各自落到不同边缘节点。
- 日期解析一律 `CultureInfo.InvariantCulture`；否则中文系统解析不了 RFC 1123，
  `If-Range` 静默不发，续传退化成全量重下。
- 侧车崩溃后由 Dart 侧指数退避重启，并按检查点自动重新入队；10 秒心跳检测「活着但不响应」。
- 侧车接受 `--parent-pid`，宿主进程消失时自我了断，不留孤儿下载进程。
- 直连、系统代理和显式 HTTP / SOCKS 代理使用不同连接池键。
- 直连时启用 Happy Eyeballs（A/AAAA 250 ms 错开竞速），IPv6 路由劣化时不再空耗整个连接超时。

### 速度口径

速度只在原生接收并写入响应 body 的位置计算：

| 指标 | 含义 |
| --- | --- |
| `rawInstantBps` | 单个采样区间的原始速度 |
| `windowBps` / `instantBps` | 250 ms 采样后的 EWMA 显示速度 |
| `averageBps` | 累计 wire bytes / active transfer time |
| `activeTicks` | 不含暂停和重试退避的活动传输时钟 |

小文件在第一个显示窗口前完成时不伪造瞬时速度，只在完成事件提供真实平均速度。

## 默认内核变更条件

当前默认仍为 NSFX。只有长期稳定性、恢复正确性和性能门槛都通过后，才会讨论默认内核变更。NSFX 会继续改进，确保它始终是独立可用的稳定内核。
